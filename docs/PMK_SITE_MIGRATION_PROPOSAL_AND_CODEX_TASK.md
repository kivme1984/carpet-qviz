# Перенос сайта «Промой Ковер» с Tilda на собственный сервер

## Назначение документа

Этот документ задаёт архитектуру нового сайта и порядок переноса существующих блоков Tilda. Он не требует немедленно переделывать дизайн. Первая цель — создать отдельный управляемый сайт на собственном сервере, сохранить существующие кодовые блоки и подготовить замену родных блоков Tilda.

## 1. Правильный репозиторий

Полный сайт нельзя размещать в репозитории PMK CRM. Сайт должен быть отдельным приватным репозиторием:

- рекомендуемое имя: `pmk-site`;
- видимость: private;
- основная ветка: `main`;
- рабочая ветка первого этапа: `feature/site-cms-foundation`.

Репозиторий `carpet-qviz` используется только как источник существующего квиза и документации по переносу. После создания `pmk-site` нужные файлы квиза копируются в новый проект с сохранением истории или ссылкой на исходный commit.

## 2. Цель

Создать независимый от Tilda сайт на собственном сервере с полноценной административной панелью. Сначала перенести существующие HTML/CSS/JS-блоки с сохранением поведения, затем постепенно заменить родные блоки Tilda собственными React-компонентами без повторной переделки всего сайта.

## 3. Рекомендуемый стек

- Next.js App Router;
- TypeScript strict mode;
- Tailwind CSS;
- Payload CMS в том же Next.js-приложении;
- PostgreSQL;
- Docker Compose;
- Caddy или Nginx как reverse proxy и HTTPS;
- S3-compatible storage для production-медиа, локальный volume для development;
- GitHub Actions для проверок и сборки;
- Playwright для smoke/E2E-проверок;
- Vitest или Jest для модульных тестов.

## 4. Главный архитектурный принцип

Не переносить сайт как один большой статический HTML-файл. Не создавать в админке свободный редактор JavaScript для менеджеров.

Сайт должен состоять из типизированных блоков. Контент, изображения, цены, ссылки и разрешённые визуальные настройки редактируются в CMS. Исходный код и сложная логика остаются в GitHub.

Для временного переноса сложных кодовых блоков допускается `LegacyTildaBlock`, но он должен:

- быть зарегистрирован разработчиком в коде;
- иметь уникальный идентификатор;
- хранить исходники в репозитории;
- не позволять обычному менеджеру вставлять произвольный JS;
- быть доступен для редактирования только ролям `owner` и `developer`;
- содержать описание зависимостей и план замены на нативный React-компонент.

## 5. Этапы переноса

### Этап A. Основа сайта

1. Создать Next.js + Payload CMS + PostgreSQL.
2. Настроить `/admin`.
3. Реализовать пользователей и роли.
4. Добавить черновики, публикацию, версии, восстановление и preview.
5. Создать конструктор страниц из массива блоков.
6. Настроить общие параметры сайта, меню, подвал, SEO, медиа, формы и редиректы.
7. Подготовить Docker-развёртывание, backup и restore.

### Этап B. Кодовые блоки Tilda

Для каждого HTML/CSS/JS-блока:

1. Сохранить исходник в `migration/tilda-source/<page>/<block-name>/`.
2. Зафиксировать исходный URL страницы и номер блока Tilda.
3. Снять скриншоты desktop/tablet/mobile.
4. Выявить зависимости от Tilda API, классов, jquery, событий и внешних файлов.
5. Изолировать CSS и убрать конфликтующие глобальные селекторы.
6. Перенести изображения в медиатеку.
7. Завернуть блок в React-компонент или безопасный legacy-адаптер.
8. Вынести тексты, изображения, кнопки, ссылки, цены и настройки в CMS.
9. Проверить адаптивность и поведение.
10. Добавить запись в реестр миграции.

### Этап C. Родные блоки Tilda

Родные блоки Tilda нельзя перенести как исходный код. Для каждого такого блока:

1. сохранить тексты, изображения, ссылки и настройки;
2. снять эталонные скриншоты в трёх разрешениях;
3. создать соответствующий React-блок;
4. добавить поля управления в CMS;
5. провести визуальное сравнение;
6. заменить блок на staging;
7. после приёмки удалить временную зависимость от Tilda.

### Этап D. Переключение домена

1. Сохранить действующие URL.
2. Подготовить 301-редиректы.
3. Проверить title, description, H1, canonical, OG, robots.txt и sitemap.xml.
4. Проверить формы, квиз, аналитику и цели.
5. Оставить Tilda активной до приёмки staging.
6. Переключить DNS только после полного smoke-теста.

### Прайс и калькулятор

Все цены должны храниться в PostgreSQL через CMS, а не внутри JavaScript.

Нужны сущности:

- услуги;
- категории ковров;
- единицы расчёта;
- правила цены;
- условия по материалу, высоте ворса, ширине и площади;
- минимальный заказ;
- доставка;
- скидки;
- дополнительные услуги;
- дата начала действия;
- активность;
- приоритет;
- история изменения.

Квиз получает активные правила через серверный API. Перед сохранением заявки сервер обязан повторно выполнить расчёт и сравнить его с клиентским результатом.

Исходные параметры для seed:

- актуальный прайс от 30.03.2026;
- минимальный заказ: 1800 ₽;
- бесплатная доставка по Нижнему Новгороду;
- доставка в область до 10 км: 500 ₽;
- срок: 3–7 рабочих дней;
- скидка постоянному клиенту: 10%;
- озонация 300 ₽/ковёр должна быть создана как неактивное правило до отдельного подтверждения, так как она есть в материалах квиза, но отсутствует в основном прайсе.

### Формы и заявки

Каждая заявка сначала сохраняется в БД сайта, затем передаётся в PMK CRM через адаптер/webhook.

Сохранять:

- имя;
- телефон;
- комментарий;
- страница и форма;
- выбранные услуги;
- результат квиза;
- серверный расчёт;
- UTM;
- referrer;
- дата и время;
- согласие;
- статус обработки;
- статус отправки в CRM;
- текст ошибки интеграции.

Обязательны:

- серверная валидация;
- защита от повторной отправки;
- rate limit;
- honeypot или CAPTCHA по необходимости;
- повторная отправка в CRM через очередь;
- журнал интеграционных ошибок без лишних персональных данных.

## 8. Роли

- `owner`: полный доступ;
- `developer`: кодовые адаптеры, интеграции, системные настройки;
- `editor`: страницы, блоки, медиа и публикация;
- `manager`: заявки, цены и обычный контент без доступа к коду, пользователям и секретам.

Нужен журнал действий пользователей.

## 9. Инфраструктура и безопасность

- отдельные `.env` для development/staging/production;
- `.env.example` без секретов;
- PostgreSQL доступен только внутри Docker network;
- HTTPS через reverse proxy;
- persistent volumes;
- ежедневный backup PostgreSQL;
- backup медиа;
- проверенный сценарий restore;
- healthcheck контейнеров;
- ограничение размера загрузок;
- Content Security Policy;
- secure cookies;
- rate limiting;
- логирование ошибок без раскрытия персональных данных;
- секреты не коммитить;
- arbitrary JS недоступен обычным пользователям.

## 11. CI

На pull request запускать:

- install с lockfile;
- lint;

## 12. Критерии приёмки первого этапа

1. Проект запускается через Docker Compose.
2. Админка доступна по `/admin`.
3. Owner может создать страницу, добавить блоки, изменить порядок, сохранить черновик, открыть preview и опубликовать.
4. Изменение контента не требует правки кода.
5. Роли ограничивают доступ.
6. Прайс загружается из CMS.
7. Квиз использует серверный расчёт.
8. Форма сохраняет заявку в БД даже при недоступной CRM.
9. Версии и восстановление работают.
10. Медиа сохраняются после пересборки контейнеров.
11. Редиректы управляются из CMS.
12. Есть документация по запуску, deployment, backup/restore и созданию нового блока.
13. Дизайн на этом этапе не переделывается.
14. Production-домен и Tilda не отключаются.

# Задача для Codex

## Сначала решить вопрос с пустой рабочей папкой

Если рабочая папка пуста, не останавливайся. Выполни следующие действия:

1. Проверь `git --version` и `gh auth status`.
2. Создай каталог проекта в `work/pmk-site` и перейди в него.
3. Если приватный репозиторий `kivme1984/pmk-site` уже существует — клонируй его.
4. Если его нет и GitHub CLI авторизован — создай его командой:

```bash
mkdir -p work/pmk-site
cd work/pmk-site
git init -b main
gh repo create kivme1984/pmk-site --private --source=. --remote=origin
```

5. Получи этот документ из ветки `docs/site-migration-task` репозитория `kivme1984/carpet-qviz`:

```bash
mkdir -p docs
curl -fsSL \
  https://raw.githubusercontent.com/kivme1984/carpet-qviz/docs/site-migration-task/docs/PMK_SITE_MIGRATION_PROPOSAL_AND_CODEX_TASK.md \
  -o docs/PMK_SITE_MIGRATION_PROPOSAL_AND_CODEX_TASK.md
```

6. Получи исходники квиза во временную папку, не смешивая Git-истории:

```bash
git clone --depth 1 https://github.com/kivme1984/carpet-qviz.git ../carpet-qviz-source
```

7. Создай первый commit с документацией, `.gitignore`, `.env.example` и README.
8. Создай ветку:

```bash
git checkout -b feature/site-cms-foundation
```

9. Реализуй основу по настоящему документу.
10. Не трогай `kivme1984/pmk-crm`.
11. Не отключай Tilda и не меняй DNS.
12. Не добавляй реальные секреты.
